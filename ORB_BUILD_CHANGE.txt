# ORB_BUILD_CHANGE — B1/B2/B3 opening-sequence re-audit (saved detail)

I re-audited the exact repository state, the BUILD-4 plan branch, the existing ORB code, the M3.1/M3.3 pattern infrastructure, and the open-source options.

The previous plan is directionally correct, but there is one major architectural correction that makes it substantially safer:

> **Do not build a brand-new `OpeningSequenceFactsV1` calculator.**
>
> Most of the raw candle work already exists in canonical M3.1.
>
> Build a thin **`OrbOpeningSequenceViewV1`** that composes existing canonical facts into an ORB-specific B1 → B2 → B3 sequence.

That avoids rewriting BUILD-0/1/2/3, avoids recalculating candle anatomy, avoids importing unsafe chart-pattern code into live ORB, and fits the repository's existing M3/M4 architecture.

## 3. I found an especially important semantic trap

This could otherwise create a very subtle bug.

The existing field:

```text
range_atr
```

inside `candle_anatomy.py` is **not Wilder ATR**.

The canonical `snapshot_feature_kernel.py` explicitly documents that the historical candle-anatomy implementation uses:

```text
rolling mean candle range
```

and preserves it under `average_range`.

The file explicitly warns that a future true ATR must be separately versioned instead of silently changing the math.

So this would be dangerous:

```text
B1_range_atr = 2.8
→ interpret as B1 = 2.8 × daily ATR
```

That is not necessarily what the current field means.

The new ORB sequence must distinguish:

```text
range_vs_mean_intraday_range
```

from:

```text
range_vs_canonical_ATR
```

They are different facts.

**Do not change the existing M3.1 field.** Preserve compatibility and make the ORB view explicitly record the normalization basis.

That is exactly the kind of hidden semantic bug your “do not modify old working code” policy is meant to prevent.

## 10. A major timing problem needs first-class handling

Assume session open is 09:15.

Three-minute bars:

```text
B1 09:15–09:18
B2 09:18–09:21
B3 09:21–09:24
B4 09:24–09:27
B5 09:27–09:30
```

Now:

```text
ORB5  locks 09:20
```

B2 straddles the OR lock.

It is neither:

```text
pure opening-range candle
```

nor:

```text
pure post-range confirmation candle
```

So add:

```text
PRE_OR_LOCK
POST_OR_LOCK
CROSSES_OR_LOCK
```

at the bar/reference level.

A `CROSSES_OR_LOCK` candle must not masquerade as a clean post-break confirmation.

That detail will remove many false historical “perfect confirmation” results.

## 12. The chain of research questions I would use

This is the auditable reasoning chain for every developing ORB sequence:

1. **Are we looking at the correct instrument, contract and exchange session?** If not, stop.
2. **Are B1/B2/B3 completely closed, contiguous and available by the decision timestamp?** If not, the sequence is incomplete.
3. **How were the candles anchored and aggregated?** If the bar boundary is ambiguous, do not compare it with historical sequences.
4. **Where does each candle sit relative to OR lock?** Pre-lock, post-lock or straddling the lock have different meanings.
5. **What facts already exist in M3.1/B3?** Reuse them; do not recalculate candle anatomy, PDH/PDL/PDC, VWAP or established price facts.
6. **What changed from B1 → B2 → B3?** Extension, retracement, overlap, higher/lower highs/lows/closes and level interactions.
7. **Was an important level merely touched/wicked through, or did price actually close and remain beyond it?** These are different states.
8. **Which competing path currently fits?** Continuation, rejection/failure, pullback-and-reclaim, or balance/no-edge.
9. **What must happen next for each hypothesis to remain valid?** Register those observations before seeing the next candle.
10. **Does B1/B2/B3 add information beyond existing ORB/gap/PDH/RVOL/structure facts?** BUILD-8 must prove that.
11. **Can existing M3.3 bounded analog retrieval explain similar historical situations?** Test that before introducing another library.
12. **Does a new metric such as STUMPY or DTW improve unseen results after costs and independent-episode controls?** If not, remove it.

That is the reasoning loop I would encode in the research plan.

## 17. STUMPY becomes a challenger, not the default

STUMPY is genuinely useful. It is designed for matrix-profile time-series analysis, motif discovery, multidimensional motifs and streaming updates. Its standard matrix-profile distance is based on z-normalized subsequence comparison. ([Stumpy Documentation][1])

But your repository already says:

> reuse canonical analogue distance unless another metric is separately proven.

So the correct sequence is:

```text
B9-A
existing M3.3 fixed feature-vector distance

        ↓ if inadequate

B9-B
STUMPY research challenger

        ↓ only if incremental benefit exists

B9-C
DTW top-K reranker
```

DTAIDistance supports multidimensional DTW and is Apache-2.0 licensed, making it technically suitable as an isolated research challenger. ([DTAIDistance][2])

Do not run DTW over the entire historical corpus every 3 minutes.

Use:

```text
cheap canonical retrieval
        ↓
top 20 / top K independent episodes
        ↓
optional DTW reranking
```

```text
   /     /   X
```

you need important swing highs.

SciPy `find_peaks` supports controls such as peak distance, width and prominence, which makes it useful for filtering insignificant fluctuations. ([Stumpy Documentation][3])

Then the system can detect:

```text
opening high

lower high #1

lower high #2
```

which is another important clue that the opening move is failing.

### 22. Stock-pattern becomes useful later

The original `stock-pattern` repository can detect classical structures such as VCP, doubles, triangles and harmonic patterns, but its own documentation says it detects patterns rather than providing buy/sell decisions. ([GitHub][4])

Therefore use it for this:

```text
Opening-event detector
        +
later classical structure detector
```

Example:

```text
09:15
opening spike/rejection

10:15+
descending triangle begins forming

11:00
triangle detector identifies compression
```

Now the engine has both:

```text
CAUSE / CONTEXT
opening spike failure

STRUCTURE
descending compression
```

That's considerably more useful.

### 23. PatternPy is not where I would start

PatternPy can provide support/resistance and structural feature ideas, but I would not make it a core dependency for this engine.

It also carries a CC BY-NC-SA 4.0 licence with a non-commercial restriction, which matters if TrendForge may become commercial. ([GitHub][5])

Use mathematical ideas where appropriate, but don't unnecessarily couple your production engine to it.

### 24. The most important prediction to create

Do **not** train:

```text
Will price go DOWN?
```

That's too vague.

Train several concrete outcomes.

At the close of B3 ask:

```text
P(touch PDH within next 5 candles)

P(close below PDH within next 10 candles)

P(recover B1 high before touching PDH)

P(make new session high within 30 minutes)

P(move -1 ATR before +1 ATR)

P(move -2 ATR before +1 ATR)
```

And record:

```text
MFE
MAE
time-to-PDH
time-to-new-high
time-to-failure
maximum subsequent drawdown
maximum subsequent rally
```

Now TrendForge can learn the actual **future behaviour of the shape**.

#### Main conclusion

For **this exact chart**, I would not try to teach TrendForge:

> "Find an Evening Star."

I would teach it:

```text
Where did we open?
        ↓
Were we above PDH?
        ↓
How extreme was candle 1?
        ↓
Did candle 2 accept or reject that move?
        ↓
Did candle 3 confirm the rejection?
        ↓
Is PDH still holding?
        ↓
Are lower highs beginning?
        ↓
Which historical opening events looked like this?
        ↓
What happened after them?
```

That moves you from **pattern recognition** toward a **developing-pattern prediction engine**.

And for the screenshot, the best working label at the third candle is:

#### `PDH_OPENING_SPIKE_2BAR_REJECTION_CANDIDATE`

If later price loses PDH:

#### `PDH_FAILED_BREAKOUT_SPIKE_AND_FADE`

That naming and state separation is much safer than declaring the final pattern after only three candles.
